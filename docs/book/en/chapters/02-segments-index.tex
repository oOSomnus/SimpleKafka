\chapter{Segments, Indexing, Retention, and Truncation}
As a single-file log grows, startup scans become slower, and old data cannot be deleted on its own. Kafka-style logs use multiple segments for a partition: old segments are closed, and the active segment receives appends; a sparse index maps logical offsets to byte boundaries within a segment. The index is a rebuildable acceleration structure, not the source of record truth. Log retention and truncation are different operations: retention deletes an old closed prefix, while truncation moves the tail back to an offset to repair a divergent suffix.

\lessonsection{5}{Sparse Index}
\goals{Build a recoverable sparse mapping from offsets to byte positions.}{Understand floor lookup, record boundaries, and recovery by scanning the log.}
\background{Each index entry consists of two big-endian int64 values: \pathcode{offset, position}; each entry is 16 bytes. Write one point every intervalRecords records, and always index the first record. When looking up a target offset, floor returns the greatest offset not larger than the target, allowing the read to start at a nearby valid boundary and scan forward. If no suitable entry exists, \pathcode{(baseOffset,0)} is a safe starting point. An index may be missing, truncated, or contain invalid entries; the main log remains the source of truth, so recovery should scan the log to rebuild the index.}
\providededit{The index file path, segment baseOffset, interval, and lifecycle are provided by \method{SparseIndex}; \method{SegmentLog} can rescan records.}{\pathcode{exercises/src/main/java/io/simplekafka/storage/SparseIndex.java}: \method{add(long,long)}, \method{floor(long)}, \method{rebuild(Path,long)}.}
\lessoncontract{Add entries in strictly increasing offset order with nonnegative positions; floor returns the greatest offset<=target, or the segment start at byte position zero if no entry is found. If the index is missing, its file length is not a multiple of 16, or an entry is invalid, rebuild it from the log; corruption in the log itself must still fail. Rebuilding must not make an invalid index look like trusted log data.}
\lessonhints{First write down the mathematical definition of floor: what offsets are in the candidate set, and what is the convention for an empty set?}{Separate index-read failures into “the index can be discarded” and “the primary log cannot be recovered.”}{Create records across multiple segments with an interval index, delete the index file, and observe recovery through a real read rather than checking only an in-memory map.}
\expected{With interval=4, create entries for offsets 0, 4, and 8; floor(6) returns the physical position associated with offset 4. Delete \pathcode{.index}, reopen, and read offset 6; the correct record is still returned. An index file with an invalid length can also be rebuilt, while a corrupt log still reports an error. These cases correspond to \method{Step05Test}.}
\pitfalls{If an index entry points inside a record, the reader will interpret arbitrary payload bytes as a header; using ceiling instead of floor skips the boundary before the target. If the index becomes the sole data source, a missing index loses the log. Kafka's index organization and precision/byte-offset model are more complex; this course indexes once every intervalRecords records, not at a fixed byte interval.}
\paragraph{Trusted boundaries for reads.}Positions supplied to add must come from actual appended records. On partition startup, recover the log and rebuild its index before using floor entries as trusted read hints. A persisted index that has not been rebuilt is not evidence that its positions match the current log. SegmentLog.readFrom begins at the supplied boundary without rescanning the earlier prefix.

\lessonsection{6}{Segmented Log}
\goals{Combine single-segment logs into a rolling partition log and make reads work continuously across segments.}{Understand segment boundaries, capacity estimation, indexes, and the global LEO.}
\background{PartitionLog holds multiple SegmentLog instances sorted by baseOffset. If the active segment cannot fit the next valid record, close it and create a segment whose base is the current LEO; even if one record is larger than the configured segmentBytes, it is valid as long as the record itself is legal and should occupy a new segment on its own rather than remain impossible to append. A batch may cross segment boundaries, while offsets remain continuous across the entire partition. A read first locates the target segment, then uses that segment's index floor as a hint, scans forward, and enters the next segment if needed, treating maxRecords and maxBytes as total budgets across segments. Precheck the validity of the entire batch before creating new files so known-invalid input does not change the directory structure. After the whole-batch precheck, increment the version once before the first disk write or segment roll; even a write attempt that later encounters an I/O error has already invalidated an old proof.}
\providededit{Segment creation/open/recovery, sparse indexing, and resource closing are provided for each segment. The PartitionLog skeleton provides mutationVersion() and private markMutation(); call it at the correct point when implementing append.}{\pathcode{exercises/src/main/java/io/simplekafka/storage/PartitionLog.java}: \method{append(List<RecordData>)}, \method{read(long,int,int)}.}
\lessoncontract{append returns the [first,next) interval for the entire batch, with no gaps in offsets across segments. Roll a segment before appending only when capacity is insufficient; an invalid batch must not roll first. Reads traverse segments in offset order and accumulate the total record and byte limits; a direct append to a segment does not itself roll it. Reopening an existing directory recovers LEO without allocating old offsets again. Directory discovery handles only the designated \pathcode{.log/.index} files and does not delete unfamiliar files. Each valid append batch increments mutationVersion once on the open log object; this is only an in-memory generation, not a disk field.}
\lessonhints{Base the capacity check on the complete encoded record size, not just the value length.}{Decide how each record in a batch relates to segment boundaries while keeping global offsets continuous.}{Separate tests for the initial append, append after a roll, and append after close/reopen, then verify every offset one by one.}
\expected{Configure 256-byte segments and append ten records, close and reopen, then append one more. Reads should still cover offsets 0 through 10 without duplicate offsets. Tests also cover a batch crossing a segment boundary, a single record occupying its own segment, and directory/LEO remaining unchanged before and after an invalid oversized record. These cases correspond to \method{Step06Test}.}
\pitfalls{Using only raw payload size for capacity omits the fixed header, length, and CRC; checking offsets separately for each batch can create conflicts across segments. Real Kafka segments more often roll by byte size and combine index files with time-based policies; this course also rolls by capacity, but the index interval is a record count. A single-segment append intentionally does not roll segments.}

\lessonsection{7}{Log Retention}
\goals{Safely delete expired closed segments while retaining the active segment and current LEO.}{Distinguish the log start, consumer progress, and deletion of individual records.}
\background{The partition log has only one retained range: \pathcode{[logStartOffset, LEO)}. This course performs retention through an explicit call; it does not run a background timer. \method{deleteBefore(offset)} deletes only closed segments whose last record offset is less than the threshold; it cannot split a segment by record and cannot remove the active segment. The new start must lie on an actual segment boundary. A consumer requesting data that has already been deleted receives \method{OFFSET_OUT_OF_RANGE}; its position is not silently changed to the new start. Consumer-group offset commits are independent of physical log deletion, and advancing a consumer position does not trigger retention automatically. Increment this log object's mutationVersion once only when at least one segment is actually deleted; a call with an invalid threshold or no deletable segment leaves the version unchanged.}
\providededit{The multi-segment directory scan, log start, and segment-closing path are held by the \method{PartitionLog} skeleton; \method{mutationVersion()} and private \method{markMutation()} are provided.}{\pathcode{exercises/src/main/java/io/simplekafka/storage/PartitionLog.java}: \method{deleteBefore(long)}.}
\lessoncontract{Delete only qualifying closed segments and the \pathcode{.index} with the same base; do not delete the active segment or unfamiliar files. Return the actual new logStartOffset. LEO does not move backward; after reopening, the new start remains correct. If an existing read position is below the new start, the read must report an explicit range error and must not seek automatically. Mark once before deletion begins; a no-op does not increment mutationVersion.}
\lessonhints{Use segment bases and the next segment's base to determine which logical offsets belong to the deletable prefix.}{Consider an empty active segment and a nonempty active segment separately; do not treat “the last segment” as deletable.}{After deletion, close and reopen, then read from both before and after the boundary to verify that disk files and the in-memory start agree.}
\expected{Create three segments, retain the last active segment, and delete old closed segments; logStartOffset moves to the retained boundary. Reopening returns the same start and leaves LEO unchanged. A read below the new start reports \method{OFFSET_OUT_OF_RANGE}. These cases correspond to \method{Step07Test}.}
\pitfalls{Deleting only \pathcode{.log} and not its paired index creates a dangling index; deleting the active segment based on the threshold loses the append starting point. Real Kafka retention is often triggered in the background by time/size configuration and may relate to consumer progress independently; this course provides only an explicit synchronous call and does not reset consumer positions.}

\lessonsection{8}{Tail Truncation}
\goals{Truncate the log tail back to a next-record offset, remove divergent tail data, and restore an appendable state.}{Understand half-open intervals, record boundaries, and segment bases.}
\background{The truncation target \pathcode{nextOffset} means retain all records with offset<nextOffset; the valid range is [logStartOffset,LEO]. If the target is exactly at an existing segment boundary, an active segment must begin at that base so appends can continue. If the target is within a segment, truncate at the physical boundary of that record, delete later segments, and rebuild the retained segment's index. Truncating to LEO is a no-op; truncating to logStartOffset leaves an empty segment, and the next append uses that offset. Truncation changes only the local log tail; it does not automatically change replication state, HW, or consumer positions. Before the first write or deletion, increment this object's mutationVersion once for a valid non-no-op truncation; invalid calls and no-ops do not increment it.}
\providededit{Segment closing, file truncation, index rebuilding, and the global segment table are established in earlier steps. The PartitionLog skeleton provides mutationVersion() and private markMutation(); a valid truncation must call it before the first file change.}{\pathcode{exercises/src/main/java/io/simplekafka/storage/PartitionLog.java}: \method{truncateTo(long)}.}
\lessoncontract{Only nextOffset values in [logStartOffset,LEO] are allowed; an out-of-range value is rejected and the log remains unchanged. Retain offsets <nextOffset and remove all later data and its indexes; update LEO to nextOffset. After success, an append can happen immediately and the new record's offset is exactly nextOffset. Unfamiliar files cannot be deleted. Invalid parameters and truncating to the current LEO do not increment mutationVersion; mark any valid content change before the first I/O.}
\lessonhints{Think of the target as “the offset to write next,” not the offset of the last record to retain.}{List the disk state for truncation inside a segment, at a segment boundary, at the current LEO, and at logStartOffset.}{Reopen the truncated directory and append one record; checking only the in-memory nextOffset is not enough to prove that indexes and files agree.}
\expected{After writing offsets 0–8, run \pathcode{truncateTo(5)}; offsets 0–4 remain readable, offsets 5–8 are not returned, and reading the new LEO 5 yields an empty result. The next append receives offset 5. \pathcode{truncateTo(LEO)} leaves contents unchanged; truncating to the start retains an empty active segment and appends from that start. These cases correspond to \method{Step08Test}.}
\pitfalls{Misreading nextOffset as the last retained record creates an off-by-one error; truncating the file without rebuilding the index can make later reads jump to deleted divergent records. Real Kafka truncation is often coordinated with leader epochs, HW, and replica protocols; this step provides only a log primitive and cannot by itself establish a safe election.}
