\chapter{Consumer Groups, Rebalancing, and Commit Fencing}
A consumer group lets multiple consumers cooperate to read a topic: each partition is assigned to one member at a time, and membership changes can change the assignment. Knowing “who reads which partition” is not enough; an old member might continue committing old progress after a rebalance, so a generation token is required for fencing. The course deliberately implements an immediately rebalanced, single-topic model, not the complete Kafka classic protocol or the newer consumer group protocol. The coordinator is trusted local state and does not provide HA.

\lessonsection{17}{Partition Assignment}
\goals{Implement deterministic, balanced Round Robin assignment with exactly one owner per partition.}{Understand set deduplication, stable sorting, and quotient/remainder distribution.}
\background{If input-set order depends on the network, a HashMap, or startup order, the same group of members may receive an unstable assignment. The course first sorts TopicPartition values by topic/partition and members by lexicographic string order, then assigns the i-th partition to member[i mod n]. The result is reproducible, and partition counts differ by at most 1 among members. Every known member must appear in the result, even if its partition list is empty; with no members, return an empty map. The shared-topic requirement is checked by the coordinator; the assignor only processes the partitions and members it is given.}
\providededit{The TopicPartition value type and group-coordinator dependency interface are provided; the scheduling algorithm is implemented by a single assignor.}{\pathcode{exercises/src/main/java/io/simplekafka/group/RoundRobinAssignor.java}: \method{assign(List<TopicPartition>,List<String)}.}
\lessoncontract{First deduplicate and sort the inputs in a fixed order. Every distinct partition must appear exactly once, and its owner must be a member; retain members with empty lists. If there are no members, the result is empty. The difference between the largest and smallest number of partitions assigned to any members must be no greater than 1.}
\lessonhints{Express the unique-owner property as two checkable conditions: complete coverage and no duplicates.}{First make the member order explicit; the original order of the input List is not the course's stable order.}{Work out five partitions with two members and five partitions with seven members by hand, then test that duplicate input does not assign a partition more than once.}
\expected{For five sorted partitions and members \pathcode{A} and \pathcode{B}, A gets three and B gets two; with seven members and five partitions, five members get one each and two have empty lists. Shuffling input order still produces the same result. See \method{Step17Test}.}
\pitfalls{Returning only members that have partitions loses explicit empty assignments; assigning by the incidental order of a map makes behavior hard to test and reproduce. Real Kafka has multiple assignors, static membership, cooperative rebalancing, and more; this course implements only a simple, single-topic Round Robin and it must not be equated with Kafka's default or complete protocol.}
\lessoncommand{17}
\lessonquestions{Why is stable sorting part of observable behavior rather than mere output polish?}{When there are more members than partitions, how do empty assignments help the caller express group state?}

\lessonsection{18}{Membership and Rebalancing}
\goals{Manage the group membership set and generation, and update all assignments when the topology changes.}{Understand that a generation is neither a timestamp nor a consumer offset.}
\background{Members of a group subscribe to the same topic. When a member joins or an existing member leaves, the assignment changes and the generation increments; a group starts at generation 0. Repeating join for the same member and topic only refreshes its heartbeat and does not create a new generation; changing the subscribed topic is illegal in this simplified model. Each change requires recalculating the complete assignment from the new member set; do not temporarily assign partitions only to the joiner while forgetting to revoke partitions from other members. When the group becomes empty, retain the generation and committed offsets so that later group state is not confused with consumer progress.}
\providededit{The group lock, member-state container, TimeSource, assignor interface, and generation lifecycle are provided by the constructor.}{\pathcode{exercises/src/main/java/io/simplekafka/group/GroupCoordinator.java}: \method{join(String,String,String)}, \method{leave(String,String)}, \method{assignment(String,String)}; extend the handler with the corresponding API.}
\lessoncontract{The first join has generation=1; a real topology change increments it exactly once and returns the latest assignment for the entire group. Repeating an identical join does not increment it; a different topic reports \method{INVALID_REQUEST}. leave/assignment for an unknown member reports \method{UNKNOWN_MEMBER}. Retain state and offsets after the group becomes empty.}
\lessonhints{First identify events that change the member set, then distinguish repeated requests from new state.}{After rebalancing, every member still in the group must see the full mapping for the same generation.}{Manually list generations and owners for the sequence A joins, B joins, A leaves, then check a subsequent join after the group is empty.}
\expected{A's first join returns generation 1; after B joins, generation is 2 and both members share all partitions; after A leaves, it is 3 and B gets every partition. Repeating A's join for the same topic does not increment the generation. See \method{Step18Test}; JOIN, ASSIGNMENT, and LEAVE are all checked through the real TCP broker API.}
\pitfalls{Advancing each member's assignment version separately can make group tokens disagree; destroying the offset store when the group becomes empty loses restart progress. Real Kafka has a complete coordination protocol with join, assignment synchronization, cooperative revocation, and other phases; the course reassigns immediately and does not simulate the full classic barrier or KIP-848.}
\lessoncommand{18}
\lessonquestions{Why must members who did not leave also receive a new assignment when the group generation changes?}{Why can consumer progress be retained when a group has no members?}

\lessonsection{19}{Heartbeats and Expiration}
\goals{Detect member timeouts under a controllable clock, and atomically process all expired members of the same group as one topology change.}{Understand heartbeat time and the expiration threshold.}
\background{Each member stores lastHeartbeat, which is refreshed by a successful heartbeat. A member expires when \pathcode{now-lastHeartbeat >= sessionTimeoutMillis}. Time comes from the injected TimeSource, so tests do not need real sleep. An expiration call may find multiple expired members at once; a single expire call must remove all expired members in the same group together, increment the generation only once, and rebalance only once, avoiding meaningless multiple generations from a single heartbeat tick. Check for an unknown-member error before refreshing; an old-generation error must not extend a member's lifetime either. Periodic scheduling is triggered by the provided facilities, but behavior tests can call expire directly.}
\providededit{The injected TimeSource, group lock, session timeout, and scheduling lifecycle are provided; tests can use a deterministic clock.}{\pathcode{exercises/src/main/java/io/simplekafka/group/GroupCoordinator.java}: \method{heartbeat(GroupToken)}, \method{expire()}; \pathcode{exercises/src/main/java/io/simplekafka/broker/BrokerHandler.java}: the \method{HEARTBEAT} branch.}
\lessoncontract{The boundary uses >=. A heartbeat with a valid current token updates the time; an unknown member reports \method{UNKNOWN_MEMBER}, and an expired generation reports \method{ILLEGAL_GENERATION}; failures do not refresh the time. expire returns the removed \pathcode{group/member} identifiers; expiration of multiple members in the same group increments the generation only once. Leader/partition concepts are not part of this state.}
\lessonhints{Keep clock reads, timeout checks, and member removals within a consistent state observation.}{The return value should distinguish exactly which member was removed from which group, not just return a count.}{Test the timeout=100 boundary at times 1099 and 1100, and refresh B before comparing it with A.}
\expected{With initial time 1000 and timeout=100, A remains at time 1099 and is removed at 1100; after B heartbeats at 1099, B still remains at 1100. If A and C in the same group expire at the same time, the generation increments only once. See \method{Step19Test}; heartbeat is tested through the real TCP API, while expiration is triggered by an injected clock without sleep.}
\pitfalls{Using real system time and sleep makes tests sensitive to scheduler jitter; changing lastHeartbeat before validating the token lets an old member renew its lifetime illegally. Real Kafka's session timeout and heartbeat behavior is more complex due to the protocol, consumer configuration, and network scheduling; this course verifies deterministic state transitions inside the coordinator only.}
\lessoncommand{19}
\lessonquestions{Why must the equality boundary be part of the expiration contract?}{Why should multiple members in the same group expiring in one expire call not cause multiple generation increments?}

\lessonsection{20}{Consumer Group Fencing}
\goals{Combine group assignment and offset operations, using a generation token to reject writes from zombie members.}{Understand the token's group/member/generation triple and revoked partitions.}
\background{A GroupToken consists of group, member, and generation. When FETCH or COMMIT carries a token, the coordinator must validate that the member exists, the generation is current, and the partition is currently assigned to that member. A consumer with an old generation cannot commit; validation and OffsetStore.commit must be in one atomic critical section under the coordinator lock, with lock order coordinator then store and no partition lock held. GroupConsumer heartbeats before each poll. On \method{ILLEGAL_GENERATION}, it queries the current assignment, discards old positions for revoked partitions, resumes new partitions from committed offsets, and fetches with the new token; \method{UNKNOWN_MEMBER} does not trigger an automatic rejoin and requires an explicit subscribe. A manual token=null preserves manual mode and does not pretend to be a group member.}
\providededit{The group messages, RpcClient, SimpleConsumer pull/offset path, and member-lifecycle skeleton are provided; broker requests with tokens are already encoded.}{\pathcode{exercises/src/main/java/io/simplekafka/group/GroupCoordinator.java}: \method{validate(GroupToken,TopicPartition)}; \pathcode{exercises/src/main/java/io/simplekafka/client/GroupConsumer.java}: \method{subscribe(String)}, \method{poll(int,int)}, \method{commitSync()}; synchronously add the handler fencing.}
\lessoncontract{A token outside the current generation reports \method{ILLEGAL_GENERATION}; an unknown member reports \method{UNKNOWN_MEMBER}; an unassigned partition reports \method{NOT_ASSIGNED}. Failure does not modify the store. Once a new assignment takes effect, an old position for a revoked partition cannot be committed. Commit validation and append complete within one coordinator-lock scope. The server does not guarantee revocation of cached records already sent to an old member; it guarantees only commit fencing.}
\lessonhints{Request validation must check token identity, current generation, and partition owner; comparing only the group name is insufficient.}{After expiration, which old positions can the consumer retain, and which must it rebuild from committed offsets?}{Create two real TCP consumers, have the old member commit a larger offset with its old token, then check that the store is unchanged after the failure.}
\expected{A joins at generation 1, then B joins and causes generation 2; A's commit of 100 with the old token is rejected, while B commits 7 with a valid token and the store remains at 7. Two real consumers split four partitions; after one member expires, the other takes over and continues from the committed offset. See \method{Step20Test}.}
\pitfalls{If the lock is released after validation but before commit, a rebalance can occur in between and a zombie commit can overwrite valid progress. Treating both \method{ILLEGAL_GENERATION} and \method{UNKNOWN_MEMBER} as automatic rejoin hides identity errors. Real Kafka group protocols include synchronization barriers and multiple phases, and transactional commit semantics have their own constraints; the course's single-topic coordinator, shared-JVM authority, and local OffsetStore are not a highly available \pathcode{__consumer_offsets}.}
\lessoncommand{20}
\lessonquestions{What does generation fencing guarantee, and why can it not guarantee exactly-once external side effects?}{What race can occur if validation and offset append acquire their locks separately?}
