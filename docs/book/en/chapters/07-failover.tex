\chapter{Election, Log Repair, and Replica Readmission}
This chapter connects replica state changes into a controlled failover. Keep the model's limitations in mind: the course's authority is a trusted metadata/HW control plane in a single JVM, and leader changes are triggered explicitly by the course; this is not KRaft controller consensus and does not cover dual-leader arbitration during network partitions. Followers read leader data over real TCP, and each broker still writes its own independent log. The course chooses a clean candidate rather than trading data loss for availability; if there is no eligible candidate, the service must remain unavailable.

\lessonsection{25}{Clean Election and Leader Epochs}
\goals{Choose a candidate with the committed prefix when the old leader is offline, and invalidate requests from the old epoch.}{Understand the ISR candidate set, HW lower bound, and epoch role fencing.}
\background{Election is a role decision, not simply a choice of any online node. If the current leader is still online, return the current metadata without incrementing the epoch. Otherwise, choose only from the old ISR among brokers that are online and have LEO>=authority.HW, using the smallest broker id; a replica below the known commit boundary cannot be a clean candidate. If there is no candidate, report \method{NO_ELIGIBLE_LEADER}, do not change epoch/HW, and do not perform an unclean election. A successful role change increments the epoch, fences the old leader, makes the new leader the only initial ISR member, and puts the other members in recovering state; they must be repaired and admitted before they can participate in acknowledgments again. Wake old-epoch producer requests that are waiting and fail them.}
\providededit{The authority owns broker online state, partition locks, LEO/HW, and role publication; reuse the three brokers' existing transports and logs.}{\pathcode{exercises/src/main/java/io/simplekafka/replication/LeaderElection.java}: \method{elect(TopicPartition)},\newline \method{checkLeader(int,TopicPartition,int)}.}
\lessoncontract{If the current leader is online, return metadata and epoch unchanged. Switch only to the smallest broker id in the old ISR that is online and has LEO>=HW; on success, increment epoch exactly once, do not roll HW back, and initialize the new ISR with only the leader. Failure for lack of candidates does not change state. A request with an old epoch reports \method{FENCED_EPOCH}; a request with the correct epoch from a broker that is not leader reports \method{NOT_LEADER}.}
\lessonhints{To list eligible candidates, first apply the ISR restriction, then check online status and LEO/HW.}{Check “epoch is correct” and “requester is leader” separately; they represent different reasons for rejection.}{Construct three replicas: the old leader is offline, one ISR candidate is below HW, and one online replica is not in ISR; verify that only a candidate satisfying every condition can be elected.}
\expected{A is the epoch 0 leader, and HW=3; after A stops, the smallest broker B in the old ISR with LEO>=3 is elected at epoch 1, and offsets 0–2 are readable. Produce/fetch requests with the old epoch are fenced. If every member of the old ISR is offline, do not elect C even if it is online, and leave HW/epoch unchanged. See \method{Step25Test}.}
\pitfalls{Choosing only the most advanced online replica can introduce a non-ISR or unknown divergent log into committed history; quietly choosing a lagging replica when there is no candidate is an unclean election. Real Kafka handles elections through a controller, leader epochs, and cluster state; this course's strong-authority assumption neither covers recovery after losing the authority nor proves consistency across network partitions.}

\lessonsection{26}{Divergent-Log Reconciliation}
\goals{Find the common prefix between an old replica and the new leader, truncate an uncommitted divergence, and catch up to the leader.}{Understand HW protection, recovery reads, epoch changes, and the scope of a proof.}
\background{The course's repair uses a full-prefix scan as a teaching simplification: from offset 0 to the captured leader LEO, fetch batches using the \newline \texttt{\detokenize{recoveryRead=true}} flag in \pathcode{REPLICA_FETCH}, and compare every locally existing record with the corresponding leader record. Recovery reads can see the leader's tail above HW, but do not report replication progress or modify ISR/HW. If an existing local record at an offset < captured HW differs, report \method{CORRUPT_RECORD} without changing the file; a merely missing local record can be filled in. Before scanning, capture the current PartitionLog object's mutationVersion; after reading the complete local prefix, recheck the epoch, start, LEO, and version under the authority lock, and hold the local log monitor in the same lock order through repair and proof publication. If any modification occurs through the log API during the scan (including truncating and then appending again to reach the same LEO), report \method{REQUEST_TIMEOUT}; do not use the changed log to make a decision, truncate it, or publish a proof. Only after confirming that the state is stable may divergence be repaired starting at HW and leader contents appended; network reads remain outside the authority lock throughout. The successful proof is bound to the PartitionLog object identity and final mutationVersion, so it cannot be misused after close/reopen resets the version; this version is an in-memory generation for a single open object, not a durable checksum, and it does not detect direct disk tampering that bypasses the API. The full scan costs O(n) and is used only for explicit recovery.}
\providededit{PartitionLog's truncateTo/append, RpcClient's replica fetch, authority epoch/HW snapshots, and partition locks are provided; an old replica is not automatically treated as ISR.}{\pathcode{exercises/src/main/java/io/simplekafka/replication/ReplicaReconciler.java}: \method{reconcile(int expectedEpoch)}.}
\lessoncontract{If the expected epoch is no longer current, exit with \method{FENCED_EPOCH}. If an existing local record at an offset below the captured HW differs from the leader, report corruption and do not modify the file; a missing committed prefix may be repaired. If the local mutationVersion changes during the scan, exit with \method{REQUEST_TIMEOUT} and do not repair the log. Final revalidation, repair, and proof publication must be atomic under the authority partition lock and the established local log monitor lock order; no truncation point may be below HW. Return LEO on completion and create a proof bound to the captured epoch, leader LEO, local log object identity, and final version; admission must revalidate the proof. Do not report ISR progress during recovery.}
\lessonhints{When comparing data, distinguish “a local record is missing” from “a local record exists but differs.”}{Identify which positions are protected by the captured HW and which uncommitted suffix may change.}{Construct three cases: a committed common prefix, a divergent uncommitted tail, and a lagging empty replica; after repair, verify the disk contents at every offset.}
\expected{Offsets 0–2 are committed and A has X@3; after switching to B, B writes Y@3. After A reconciles, offsets 0–2 are unchanged, offset 3 contains Y, and LEO=4. An empty replica can also copy the complete committed prefix. If offset 1 differs on the two replicas and captured HW=3, reject the operation and leave A's file unchanged. See \method{Step26Test}.}
\pitfalls{Mechanically treating a local HW=0 as “safe to delete all data” loses the committed prefix that was actually replicated; treating a missing prefix as divergent corruption prevents normal catch-up. Real Kafka uses leader-epoch history to locate divergence and truncate precisely; KIP-101 explains why the high watermark alone is insufficient to infer a truncation point. The course's O(n) scan is for teaching and is not a production approach.}

\lessonquestions{Why should a different committed record and a missing local committed record be handled differently?}{If the leader writes again after the captured snapshot, why can the old proof not be used directly for admission?}

\lessonsection{27}{Metadata Routing Refresh}
\goals{Let clients cache metadata and route by partition leader, while avoiding automatic replay of a business request after an error.}{Understand control-plane queries, data-plane routing, and uncertain acknowledgments.}
\background{A bootstrap endpoint is only an entry point for discovery; it does not have to serve data permanently. refresh queries metadata in bootstrap order and can continue to another available node if a connection fails. call sends one business request to the leader/epoch in the cache. On receiving \method{NOT_LEADER} or \method{FENCED_EPOCH}, it may refresh the cache so the next request uses the new role, but it must propagate the original error from the original request to the caller. It must not automatically replay the business request using new metadata: the old request's error may have occurred while waiting for confirmation, after data was already appended. I/O, timeout, and storage errors are not retried automatically either. Producers, consumers, and group consumers may add a Router constructor entry point; the original RpcClient constructor continues to support single-machine mode and is not a deprecated shim. Group/offset control-plane operations use an available bootstrap control client, while partition fetch/produce is routed to the leader.}
\providededit{RpcClientFactory can connect by Endpoint; MessageCodec and the original client logic are complete; broker metadata returns the actual leader endpoint/epoch.}{\pathcode{exercises/src/main/java/io/simplekafka/client/MetadataRouter.java}: \method{refresh(String)}, \method{call(TopicPartition,Request)}; connect the Router constructor paths in \method{SimpleProducer}, \method{SimpleConsumer}, and \method{GroupConsumer}.}
\lessoncontract{refresh reads metadata only and tolerates failures in bootstrap order; call uses the cached endpoint and epoch. \method{NOT_LEADER}/\method{FENCED_EPOCH} may trigger refresh, but the original response must be propagated and produce/fetch/commit must not be resent. Other network and storage errors are not retried automatically. Only a later, independent request uses the updated cache.}
\lessonhints{Make clear that one call makes exactly one business-request attempt; refresh is a control-plane action, not a retry.}{How does the order of failures across different endpoints affect the initial metadata query?}{Simulate a write rejected using stale metadata even though the server may already have appended it; check the refreshed metadata, the old receipt, and the record count, then issue the next request explicitly.}
\expected{Old metadata points to A/epoch 0. After A stops, the first routed request receives an error related to the refresh; the client refreshes to B/epoch 1 but returns that error. A second, explicit new request writes only one copy to B. If a broker appends but its response is lost, the client reports an error and does not automatically create a second record. See \method{Step27Test}.}
\pitfalls{Treating \method{NOT_LEADER} as proof that “nothing was written” can cause duplicate production; refreshing the cache but returning success to the caller fabricates a receipt. \method{MetadataRouter} refreshes but never replays a request, and \method{SimpleProducer} never retries automatically. Chapter 8 adds a separate \method{IdempotentProducer} with caller-invoked retry and durable batch identity; it does not change the ordinary producer contract or provide transactions or end-to-end exactly-once guarantees.}
\lessoncommand{27}
\lessonquestions{Why are refreshing metadata and replaying a business request two different actions?}{When a client sees an error, why can it not conclude that the server had no side effect?}

\lessonsection{28}{Replica Readmission to ISR}
\goals{Readmit a repaired replica to ISR only after strict proof, and verify an integrated failover.}{Understand replica assignment, online status, follower role, epoch, and proof validity.}
\background{Completion of replica recovery does not automatically mean that the replica is synchronized. The prefix proof generated by log repair is required to request readmission to ISR, and is bound to the captured epoch, leader LEO, local PartitionLog object identity, and mutationVersion. Under the authority partition lock, verify that the target broker is assigned and online, is currently a follower, and that the expected epoch matches the current epoch. Hold the target PartitionLog monitor until the ISR transition is published; append/delete/truncate/close use the same monitor, so there is no local log mutation window between proof validation and ISR admission. The proof must still match the current leader epoch/LEO and the same log object/version passed in the current call; log start must be 0 and current LEO must exactly equal leader LEO. Any append/delete/truncate through the PartitionLog API invalidates the old proof, even if truncating and appending restores the same LEO; reconciliation must be run again. This in-memory version cannot detect external file changes that bypass the API. On successful ISR admission, initialize reportedLEO/lastCaughtUp and recompute HW; a repeated addition of a member already in ISR returns true but does not change HW.}
\providededit{The authority's role/ISR management, replication progress, proof type, and broker lifecycle are provided by the course's base layer.}{\pathcode{exercises/src/main/java/io/simplekafka/replication/ReplicaAdmission.java}\newline: \method{tryAdd(int,TopicPartition,int)}.}
\lessoncontract{Return true only if the target replica is assigned, online, a follower for the current epoch, and the proof's leader and local log object identity/version are correct; the log start is 0 and local LEO equals the current leader LEO. Do not allow a local PartitionLog API write during proof validation; an append by the leader or any local PartitionLog change makes the old proof return false. An unassigned replica reports \method{INVALID_REQUEST}; an offline replica or stale proof returns false. A repeated call for a replica already in ISR returns true without changing the high watermark. On success, recompute HW and wake acknowledgment waiters.}
\lessonhints{Treat proof validity as a versioned fact, not a permanent Boolean flag.}{If leader LEO changes after proof generation, which state must be compared again?}{First verify admission in a simplified case with no changes; then append one leader record and try reusing the old proof; finally retry with a new proof.}
\expected{Stop A and let B take over; repair and admit surviving C, then restore minISR; write a new message with ALL. Restart A, repair and admit it, then write again with ALL. The three independent logs contain matching record bytes/offsets without gaps, and the group continues from its committed offset. Reusing an old proof after leader LEO changes must return false. See the full TCP integration acceptance test in \method{Step28Test}.}
\pitfalls{Checking only equal LEOs without comparing the prefix lets a divergent replica masquerade as synchronized; checking only the epoch at proof creation without checking the current leader LEO can omit new tail records. Real Kafka has more complex ISR admission and leader-epoch/replication protocols; the course's strict prefix proof and strong authority are verifiable teaching constraints, not a production controller design.}

\lessonquestions{Why is matching LEO insufficient to prove that two logs contain the same data?}{Why must admission recompute HW and wake requests waiting for acknowledgment?}
