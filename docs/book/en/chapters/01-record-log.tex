\chapter{Records and Single-Segment Persistence}
This chapter starts with a practical question: after a process exits, how can a message be read back from a file unchanged? Memory disappears with the process, while a file stores only bytes and does not remember which bytes belong to one record. The course first defines binary record boundaries, then appends records to an append-only log; later steps use a logical offset to identify a record and a byte position to find it in a file. LEO (log end offset) is the next offset available for append, not the last record's offset and not the file's byte length. These are course concepts, not Kafka's disk format.

\lessonsection{1}{Record Encoding and Decoding}
\goals{Define stable on-disk boundaries so writers and readers assign the same meaning to every byte.}{Understand lengths, fixed-width integers, UTF-8 bytes, and CRC32C; prior knowledge of binary formats or file scanning is not required.}
\background{Numbers and fields in a file are only bytes; a format must specify their order, width, and byte order before those bytes can be decoded. This course uses big-endian (most-significant byte first) fields: \pathcode{length:int32 | crc32c:int32 | offset:int64 | timestamp:int64 | keyLength:int32 | valueLength:int32 | key | value}. length is counted from the CRC field and excludes its own leading 4 bytes. The fixed portion occupies 32 total bytes before payload, of which the length value's fixed portion is 28 bytes. CRC32C checks whether bytes from offset through the end of value match the written checksum; it can detect common accidental corruption, but is not authentication or a security signature.}

\providededit{The \pathcode{LogRecord} type represents a record with a logical offset; \pathcode{RecordData} stores key, value, and timestamp; \pathcode{CourseException}, \pathcode{ErrorCode}, big-endian fields, and CRC32C utilities are provided.}{At repository root, implement \method{public static ByteBuffer encode(LogRecord record)} and \method{public static LogRecord decode(ByteBuffer source)} in \pathcode{exercises/src/main/java/io/simplekafka/storage/RecordCodec.java}. Do not edit provided types, the reference implementation, or tests.}
\subsubsection*{Prerequisites}
This is the first course step; you only need to read basic Java classes, methods, and exceptions. A byte is the unit used for file lengths (8 bits): one UTF-8 character may occupy multiple bytes, so lengths count encoded bytes rather than characters. The next step writes these encoded bytes to a file.
\subsubsection*{Inputs, outputs, and state}
\begin{itemize}
\item \method{encode} accepts a \pathcode{LogRecord(offset,data)}; a null record reports \method{INVALID_REQUEST}. offset and timestamp must be nonnegative \pathcode{long} values; value must be present (it may contain zero bytes); key may be null, an empty array, or a nonempty byte array. Success returns a new buffer with position=0 and limit exactly at the end of this record. It reads or changes no file state.
\item \method{decode} starts at the source's current position; a null source throws \method{NullPointerException} without consuming input. It interprets fields as big-endian, independent of the source's byte order. Heap, direct, read-only, and slice buffers are valid inputs. Success consumes exactly one record and advances position to that record's end; limit is unchanged and bytes after it remain for the next call.
\item The legal length range is 28 through 1,048,576 inclusive; total record space is \pathcode{4 + length = 32 + keyBytes + valueBytes}. A null key is written as keyLength=-1, while an empty key is 0; valueLength must be nonnegative. Ordinary records have no additional identity fields.
\end{itemize}
\lessoncontract{Incomplete input (fewer than the 4-byte length prefix, or fewer than the body declared by a legal length) reports \method{INVALID_REQUEST}. A complete but out-of-range length, invalid field structure, negative offset/timestamp, or CRC mismatch reports \method{CORRUPT_RECORD}. An invalid record passed to encode or a record over the size limit reports \method{INVALID_REQUEST}. decode must not change limit on success or failure; on failure it must not advance source position.}
\subsubsection*{A complete hand-worked record}
First use the independent golden fixture from the tests: offset=7, timestamp=23, key=null, and an empty value, with every integer big-endian. The hexadecimal fields are \pathcode{0000001c df159f32 0000000000000007 0000000000000017 ffffffff 00000000}: length=28; CRC32C is \pathcode{df159f32}; \pathcode{ffffffff} is keyLength=-1; valueLength=0. The 4-byte prefix is outside length, so the total record is 32 bytes.
\par A separate size example uses a null key and the UTF-8 value “值” (assume its bytes are \pathcode{e580bc}, 3 bytes): length=$28+0+3=31$, and total space is $4+31=35$ bytes. An empty key is encoded with keyLength=0, not -1; this is not the empty-value golden fixture above.
\expected{\method{Step01Test} compares encode/decode with independent byte goldens and covers null versus empty keys, zero-length values, consecutive decoding, several ByteBuffer views, every incomplete prefix, out-of-range lengths, CRC/structure corruption, and the maximum size. Key methods: \pathcode{encodeAndDecodeMatchIndependentBigEndianGoldenRecords} checks the golden bytes; \pathcode{decodesOneRecordFromHeapDirectReadOnlyAndSliceBuffers} checks supported views; \pathcode{rejectsEveryIncompletePrefixAndOutOfRangeRecordLength} and \pathcode{rejectsCorruptionInEveryStoredField} cover errors; \pathcode{enforcesLengthLimitAndSupportsLargestNonnegativeLogicalValues} checks the maximum. The largest ordinary record has length=1,048,576 and total size=1,048,580; one more value byte must be rejected.}
\pitfalls{Do not count the length prefix in length or include the CRC field in its own CRC range. Do not treat a Unicode character count as valueBytes. A matching CRC32C only says the protected bytes agree with the checksum; it does not prove the source is trusted.}
\lessonhints{List the 4-byte length, 4-byte CRC, two 8-byte integers, two 4-byte lengths, and variable tail separately.}{Calculate the length range, the fields it covers, and total allocation as separate quantities; convert UTF-8 to bytes before counting.}{For each failed decode, decide whether input is incomplete or complete but invalid, then verify the successful position/limit and a trailing sentinel.}
\lessoncommand{1}
\lessonquestions{Why must a null key and a zero-byte empty key use different representations?}{What does a successful CRC check tell you, and what does it not tell you?}
\paragraph*{Self-check explanation}
A null key means no key is present; an empty key means a key exists with length zero. Collapsing them loses caller data. CRC32C can detect an accidental change in protected bytes, but cannot establish sender identity or replace structural validation.

\lessonsection{2}{Log Append}
\goals{Implement continuous offset allocation for a single-segment log and complete the course's required writes before returning success.}{Reuse record encoding and understand a lock around shared state, full-write loops, and file byte positions.}
\background{Appending adds new records to the end of an existing log instead of overwriting old records. A partition log keeps shared state for the next offset and file-tail byte position; a lock is a mutually exclusive section protecting shared state, so only one append at a time can read or update those values. Without that coordination, two threads could assign the same offset or interleave batch bytes. A single \method{FileChannel.write} may write only part of a buffer; the provided \method{ChannelIO.writeFully} keeps writing until it is complete. The course requires a complete batch write and \method{force(false)} before publishing its result.}
\providededit{\method{SegmentLog.create(Path,long)} creates a segment. The segment, FileChannel, lock, baseOffset, nextOffset, \method{close()}, \method{RecordCodec.encodedSize(RecordData)}, and \method{ChannelIO.writeFully(...)} are provided.}{Implement \method{public AppendResult append(List<RecordData> records)} in \pathcode{exercises/src/main/java/io/simplekafka/storage/SegmentLog.java}.}
\subsubsection*{Prerequisites}
Complete \stepref{1}{record encoding and decoding}, especially how to calculate a record's complete encoded byte size and reject invalid records before writing. Tests start from a nonzero baseOffset, so do not assume every log starts at offset 0.
\subsubsection*{Inputs, outputs, and state}
\begin{itemize}
\item Input is a nonempty \pathcode{List<RecordData>} in append order; each item must meet Step 1's value, timestamp, and maximum-size rules. Output \method{AppendResult(firstOffset,nextOffset)} is a half-open interval: it includes firstOffset and excludes nextOffset.
\item An empty or null batch, null element, invalid data, oversized record, or an offset that cannot be incremented is rejected with \method{INVALID_REQUEST}. Known-invalid input must be detected before any disk write.
\item On success, the file grows at its tail by the entire batch and LEO advances to nextOffset. A write or force I/O failure reports \method{STORAGE_ERROR}. I/O failure may occur after some or all bytes have been written; the course does not promise rollback, so do not claim that disk is unchanged after every failure. A closed segment cannot be appended to.
\end{itemize}
\lessoncontract{Allocate consecutive offsets from the current LEO while holding the lock; keep each batch adjacent and prevent concurrent batches from interleaving. Precheck every record before writing. Return the interval and publish the new LEO only after all writes complete through writeFully and force succeeds. Invalid input leaves the file and LEO unchanged.}
\subsubsection*{A complete hand-worked append}
Create an empty segment with baseOffset=5, so its initial file is empty and LEO=5. Append three ordinary records, each with a null key and a one-byte UTF-8 value, so each occupies 33 bytes: \pathcode{append([a,b])} writes offsets 5 and 6, returns \pathcode{[5,7)}, leaves the file at 66 bytes and LEO=7; then \pathcode{append([c])} writes offset 7, returns \pathcode{[7,8)}, leaves the file at 99 bytes and LEO=8. If a later invalid record is rejected, the file and LEO remain 99 and 8, and the next valid record starts at 8.
\expected{\method{Step02Test}: \pathcode{appendsBatchesFromNonzeroBaseAndPreservesIndependentDiskEncoding} verifies [5,7), [7,8), and disk fields at base=5; \pathcode{rejectsInvalidBatchesAtomicallyWithoutCreatingOffsetGaps} checks empty/null/null-containing/oversized rejection, unchanged file/LEO, and the next offset; \pathcode{rejectsAppendAtMaximumOffsetWithoutChangingEmptyFile} checks overflow; \pathcode{concurrentBatchesReceiveDisjointRangesWithoutInterleaving} checks disjoint, noninterleaved ranges.}
\pitfalls{If an invalid third record is detected only after writing the first two, a partial batch can remain in the log. Do not substitute raw value length for RecordCodec's complete encoded size. A successful force is the course's condition for returning success, not proof that a physical medium can never lose data during a power failure.}
\lessonhints{Write down the current LEO before the call and use it as the batch's first offset; nextOffset starts the next batch.}{Separate prechecking the entire input from reading current LEO under the lock, and use writeFully for partial writes.}{In a concurrent test, check both AppendResult intervals and every file offset in order, not just the final LEO.}
\lessoncommand{2}
\lessonquestions{Why must the entire batch be prevalidated before the first disk write?}{If a write throws an I/O exception, why can't you automatically conclude that it wrote nothing?}
\paragraph*{Self-check explanation}
Whole-batch prevalidation prevents predictable parameter errors from leaving half a batch or consuming offsets. An I/O error can occur after the operating system accepted some bytes, so a failed return does not imply a disk rollback; recovery must identify a valid boundary.

\lessonsection{3}{Offset-Based Reads}
\goals{Read complete records from a logical offset while honoring both record-count and encoded-byte budgets.}{Distinguish logical offsets, file byte positions, hints, and the append cursor.}
\background{A caller uses an offset to name the first logical record it wants; a file reader needs a byte position from which to scan. An offset numbers records in a partition log, while a byte position counts bytes within this segment; they have different units and cannot be substituted for one another. bytePositionHint only reduces searching: it must be a record boundary and cannot skip the target. Results still start at the requested offset. A record cannot be split, and maxBytes counts each complete encoded record including its 4-byte length prefix. Explicit-position file reads also avoid changing the append position.}
\providededit{Segment creation, LEO, locking, and record decoding are provided; \method{read(long,int,int)} supplies the segment start as the default hint.}{Implement \method{public List<LogRecord> readFrom(long offset,long bytePositionHint,int maxRecords,int maxBytes)} in \pathcode{exercises/src/main/java/io/simplekafka/storage/SegmentLog.java}.}
\subsubsection*{Prerequisites}
Complete \stepref{2}{log append} and understand that successful appends assign consecutive offsets while the file grows by complete encoded bytes. Without a sparse index, the target can be found by scanning from the segment start; this step's hint is a physical search position, not a replacement for the logical request.
\subsubsection*{Inputs, outputs, and state}
\begin{itemize}
\item offset must be in \pathcode{[baseOffset, LEO]}; exactly LEO is a valid empty read. maxRecords and maxBytes must both be positive. Returned records have consecutive offsets and do not exceed either budget.
\item bytePositionHint is a nonnegative byte position in this segment. It must be a real record boundary and no later than the physical position for the requested offset; an EOF hint is valid only when offset=LEO. A negative, skipping, interior, or past-EOF hint reports \method{INVALID_REQUEST}; an out-of-range offset reports \method{OFFSET_OUT_OF_RANGE}; a corrupt complete stored record reports \method{CORRUPT_RECORD}; a closed segment or underlying I/O failure reports \method{STORAGE_ERROR}.
\item If the first complete record alone exceeds maxBytes, return an empty list rather than part of a record. Reads, successful or not, do not append, change LEO, or advance persistent consumer progress.
\end{itemize}
\lessoncontract{Scan forward from the verified hint boundary, skipping complete records whose offsets are before the target; output begins at the requested offset. Count each record and its complete encoded bytes only after the entire record is available. Reading does not move the append cursor.}
\subsubsection*{Hand calculation: full records, budget, and hint}
Assume base=0 and append five records in order. Each has a null key and a 1-byte value in the ordinary format, so each occupies $32+1=33$ bytes. Their offsets are 0–4, their file starting positions are 0, 33, 66, 99, 132, and EOF is 165. Calling \pathcode{readFrom(2,33,2,66)} uses hint=33, the valid boundary for offset 1; the reader skips offset 1 and still returns offsets 2 and 3. Budgets of 32, 33, 65, and 66 bytes return 0, 1, 1, and 2 records. offset=5 with hint=165 returns an empty list.
\expected{\method{Step03Test}: \pathcode{validatesRecordBoundaryHintsAndWholeRecordBudgets} checks 33-byte positions, hints -1/1/67/166, target-skipping hint 165, budgets, and errors; \pathcode{enforcesNonzeroBaseBoundsAndKeepsReadPagingSeparateFromAppendPosition} checks nonzero base and paging without moving the append position; \pathcode{rereadsCompleteRecordsAndRejectsDamageWrittenThroughAnotherHandle} checks \method{CORRUPT_RECORD} after external damage.}
\pitfalls{Treating offset=2 as file byte 2 starts in the middle of a record; treating the hint as the first returned offset changes the request's meaning. Byte budget is not just payload size: lengths, CRC, and field headers use disk space too.}
\lessonhints{Draw a two-row mapping from offsets to file starting positions and label the units.}{Check that a hint is not after the target and is a record boundary; results start at the requested offset, not the hint.}{Add complete record sizes for budgets 32, 33, 65, and 66, and separately test an empty result when the first record exceeds the budget.}
\lessoncommand{3}
\lessonquestions{If a hint points to offset 1's boundary, why must a read at offset 2 not return offset 1?}{When the first record does not fit maxBytes, why is returning part of it not reasonable?}
\paragraph*{Self-check explanation}
The hint only locates a place to begin searching; the requested offset defines the result. A partial record cannot be decoded because it contains length and checksum fields, so an empty result tells the caller that no complete record fits this budget.

\lessonsection{4}{Crash Recovery}
\goals{Recover a segment's continuous LEO after restart and truncate only a file tail that can be proven incomplete.}{Distinguish a partly written record from a complete but corrupt record.}
\background{A process may exit while writing the length, fixed fields, or value. Recovery starts from baseOffset and compares each complete record's offset with the next expected offset. Record boundaries require both length and complete fields: when EOF cannot form the next record, returning to that record's start is safe; a complete record with an invalid CRC, field, or continuous offset is corruption and must not be silently discarded.}
\providededit{\method{SegmentLog.open(Path,long)} opens an existing file and invokes recovery. File positions, baseOffset, the LEO field, and codec/read/write paths from Steps 1–3 are established.}{Implement \method{public long recover()} in \pathcode{exercises/src/main/java/io/simplekafka/storage/SegmentLog.java}.}
\subsubsection*{Prerequisites}
Complete \stepref{3}{offset-based reads} and be able to identify record boundaries from the length prefix and fixed fields. This method is called explicitly and also when \method{open} opens an old file; calling recover again after open succeeds must give the same result.
\subsubsection*{Inputs, outputs, and state}
\begin{itemize}
\item Input is an open segment and its baseOffset; an empty file may have any nonnegative base. The result is recovered LEO, the next offset for append; for an empty segment LEO=baseOffset.
\item Fewer than 4 remaining bytes means an incomplete length prefix: truncate at the current record start. A complete length outside [28,1,048,576] is \method{CORRUPT_RECORD}, even if no body is present. A legal length whose declared body is incomplete is truncated at the current record start.
\item A complete record with bad CRC/fields or an offset other than the next expected offset is \method{CORRUPT_RECORD}; reject it and leave the original file bytes unchanged. A closed segment or underlying I/O failure reports \method{STORAGE_ERROR} and preserves the I/O cause.
\end{itemize}
\lessoncontract{After successful recovery, the file contains only a continuous, complete, valid prefix, and LEO points to its end. Only an incomplete tail record may be repaired; never skip or rewrite a complete corrupt record. Repeating recovery or closing and reopening must be idempotent.}
\subsubsection*{Hand calculation: recover, then append}
Assume base=0 and the file has two complete ordinary records, each with a null key and 1-byte value. Offsets 0 and 1 occupy 33 bytes each, so the valid prefix is 66 bytes and the next expected offset is 2. The third record at offset 2 declares the same total size of 33 bytes; only its first 17 bytes are in the file (including its complete length=29 but an incomplete body), making the file 83 bytes long. recover truncates to byte position 66 and returns LEO=2; appending another one-byte value returns \pathcode{[2,3)}. In contrast, if that third record has only a complete length prefix declaring length=1,048,577, the length itself is illegal, so recovery reports \method{CORRUPT_RECORD} without truncation.
\expected{\method{Step04Test}: \pathcode{truncatesEveryIncompleteTailPrefixAndKeepsACompleteThirdRecord} and \pathcode{truncatesAnIncompleteFirstRecordAtZeroAndNonzeroBases} verify truncation only for incomplete tails; \pathcode{recoversEmptyAndNonzeroBaseFilesIdempotentlyAndRejectsWrongBase} checks empty/nonzero-base recovery; \pathcode{rejectsCompleteCorruptionAndOffsetDiscontinuitiesWithoutChangingFileBytes} checks CRC, fields, illegal length, and offset gaps leave complete corrupt files unchanged.}
\pitfalls{Treating every parse failure as a tail fragment swallows complete-record corruption; treating every EOF as a corrupt file prevents recovery from an interrupted write. Only after a legal length tells you the expected body size can you distinguish a short body from an illegal length.}
\lessonhints{The scan needs only the current valid byte boundary and the next expected offset.}{Classify “fewer than 4 prefix bytes / illegal length / legal length but short body / complete valid or complete corrupt.”}{Reopen two valid records plus a partial tail; then separately use a complete record with a bad CRC and compare error codes and file bytes.}
\lessoncommand{4}
\lessonquestions{Why can't an illegal number in a complete length prefix be treated as a body that was only partly written?}{Why does recovery return LEO=2 rather than the last record's offset=1?}
\paragraph*{Self-check explanation}
An illegal length is a complete declaration that the record format does not accept, not a legal record that lacks bytes, so it is corruption. LEO is the next append position; after a record at offset 1, the next offset is 2.
