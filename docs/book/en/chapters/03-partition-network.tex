\chapter{Partitions and a Broker on a Real Network}
The log in the previous chapter had only local meaning; this chapter creates multiple partitions for a topic, then separates clients from the broker with real loopback TCP requests. Partitions define ordered ranges of records, and topic metadata tells clients the leader of each partition. TCP is a byte stream and does not preserve the boundaries of Java writes, so the protocol must include frame lengths. This course implements only its teaching binary messages and is not compatible with the Kafka wire protocol.

\lessonsection{9}{Partition Routing}
\goals{Route the same key to the same partition consistently while providing observable rotation for null keys.}{Understand key byte identity, CRC32C, and modulo.}
\background{A producer must choose a partition before it can establish ordering within that partition. For a non-null key, this course computes CRC32C and takes the CRC as an unsigned value modulo the partition count; the same byte string therefore consistently selects the same partition. A null key has no key to hash, so one Partitioner instance rotates, starting at 0. An empty byte array is a present key of length zero, not the same as null. The partition count must be positive. This simple rule makes results deterministic and easy to observe.}
\providededit{The partitioner's round-robin state and no-argument constructor are provided; topic metadata supplies the partition count.}{\pathcode{exercises/src/main/java/io/simplekafka/client/Partitioner.java}: \method{choose(byte[] key,int partitions)}.}
\lessoncontract{partitions<=0 is an invalid request. Routing a non-null key uses the unsigned interpretation of its CRC32C; for the same instance, null keys select 0..partitions-1 in sequence and wrap around. Different instances each start from zero.}
\lessonhints{First distinguish three inputs: null, an empty array, and a nonempty array.}{Check the conversion semantics between Java's signed int and the problem's unsigned CRC so that a negative remainder cannot become a negative partition.}{Mix calls with a key, a null key, and different partition counts on the same instance; examine whether the round-robin cursor advances only for the specified inputs.}
\expected{With 3 partitions, the same key selects the same partition 100 times in a row; an empty key is also routed deterministically. A fresh Partitioner returns 0, 1, 2, 0, 1, 2 for six consecutive null-key calls. These cases correspond to \method{Step09Test}, which also checks rejection of nonpositive partition counts.}
\pitfalls{Using a key's hashCode instead of CRC32C, or taking a remainder directly from a value that may be negative, violates the routing contract. Real Kafka's default partitioner uses a different key-hash algorithm and a sticky-batching strategy for null keys; this course uses instance-level round-robin for null keys, which must not be described as Kafka's default behavior.}
\lessoncommand{9}
\lessonquestions{Why should the hash be computed over key bytes rather than a RecordData object's Java hashCode?}{How do a null key and a zero-length key array differ in the protocol and in routing?}

\lessonsection{10}{Topic Metadata}
\goals{Register a topic's fixed partition set in a safe directory structure and let clients discover leaders in a deterministic order.}{Understand partition metadata and the purpose of idempotent creation.}
\background{Metadata maps logical names to physical partitions. Each partition carries at least a TopicPartition, leader id, epoch, replica/ISR lists, and Endpoint; in single-broker mode, epoch is 0 and replicas and ISR contain only the current broker. The number of partitions for a topic is fixed when it is created in this course catalog. The directory structure is root/topic/partition. Topic names are restricted to \pathcode{[A-Za-z0-9._-]+}, with \pathcode{.} and \pathcode{..} rejected to prevent path traversal. On directory restart, explicitly create the same topic/count again to open existing logs; do not infer the total partition count from files that happen to exist.}
\providededit{Endpoint, partition metadata value types, and log registration paths are provided; the Catalog constructor fixes the broker id and endpoint.}{\pathcode{exercises/src/main/java/io/simplekafka/broker/PartitionCatalog.java}: \method{createTopic(String,int)}, \method{metadata(String)}.}
\lessoncontract{A positive partition count creates a fixed set of partitions; creating the same topic with the same count is idempotent, while a different count reports \method{INVALID_REQUEST}. An unknown topic reports \method{UNKNOWN_TOPIC_OR_PARTITION}. metadata returns entries in increasing partition-id order and does not expose paths outside root. Single-broker metadata has epoch=0 and replicas/isr=[brokerId].}
\lessonhints{Creating a topic is more than mkdir: consider the partition count and constraints that can be verified after a restart.}{Give same-name/same-count calls and same-name/different-count calls different semantics.}{Test special path characters, empty names, and reopening directories to confirm that name validation occurs before file creation.}
\expected{After creating \pathcode{orders} with 2 partitions, metadata contains \pathcode{orders-0} and \pathcode{orders-1} in a fixed order; creating the same definition again is harmless, while changing it to 3 reports an error. Querying an unknown topic returns the topic/partition error code. These cases correspond to \method{Step10Test}.}
\pitfalls{Concatenating a user topic directly into a path exposes the disk boundary to path traversal; enumerating directories to recover the partition count can treat manual leftovers as metadata. Real Kafka topic metadata is managed by a cluster control plane, and partitions can be expanded through controlled operations; this course catalog supports only an explicitly fixed count and does not handle dynamic expansion.}
\lessoncommand{10}
\lessonquestions{Why can't “same name but different partition count” be treated as idempotent success?}{What evidence can a disk directory provide, and what metadata can it not replace?}

\lessonsection{11}{TCP Frame Protocol}
\goals{Split a TCP byte stream into bounded request/response frames that can be matched.}{Understand readFully, EOF position, length prefixes, and correlation ids.}
\providededit{Messages request/success-response bodies, API id constants, the Frame value type, and ErrorCode wire ids are provided; this step does not rewrite the body codec.}{\pathcode{exercises/src/main/java/io/simplekafka/protocol/FrameCodec.java}: \method{write(OutputStream,Frame)}, \method{read(InputStream)}.}
\lessoncontract{EOF before the first byte returns null; EOF partway through a frame is \method{INVALID_REQUEST}. Reject negative or oversized lengths before allocating. The server validates and rejects unknown version/API values and nonzero request errors. Read consecutive frames from a stream one at a time without losing boundaries; never send a partial frame. Stream I/O throws IOException as specified by the interface, while protocol-format errors use course error codes.}
\lessonhints{The minimum frame length is the sum of the widths of the fixed header fields, not something to infer from an example payload.}{Handle “clean end of stream” and “end of stream inside a frame” separately.}{Feed two consecutive frames through an InputStream that returns only one byte per read, then check immediate rejection using input that contains only an oversized length prefix.}
\expected{Split a two-frame stream into single-byte chunks; two consecutive reads return the original correlation ids and payloads, and only the next read returns null. Input with only a 4-byte oversized length and no body fails immediately instead of waiting or allocating several megabytes. These cases correspond to \method{Step11Test}.}
\pitfalls{A single read that is expected to fill a header is vulnerable to TCP segmentation; allocating before checking length lets a malicious request amplify memory use. Real Kafka has its own request headers, API-version negotiation, and message formats. This course's version=1 and API list define a teaching protocol and cannot be used with official clients.}
\lessoncommand{11}
\lessonquestions{Why must a correlationId be returned with its corresponding request?}{What is the value of distinguishing “normal EOF” from “half-frame EOF” in a stream?}

\lessonsection{12}{Single-Broker Requests}
\goals{Connect metadata, produce, and fetch business requests to the local catalog and verify them end to end over real TCP.}{Know framing, body codecs, and single- and segmented-log steps.}
\background{The broker is the request-semantics boundary: validate the topic, partition, epoch, and parameters first; then call the log and finally wrap the successful result or a standard error in a Reply. In single-broker mode, log end offset is also the high watermark, so consumers can read immediately after an append. produce returns an append interval; fetch reads records using an offset and both budgets, and returns logStart, LEO, HW, and epoch. Unknown APIs are rejected at the transport layer; a business error affects only the current request, and the broker should continue accepting subsequent TCP requests. A real TCP call tests client framing and the server handler together, rather than calling methods directly.}
\providededit{\method{BrokerHarness.single} manages log registration, TCP transport, MessageCodec, request-body parsing, and service lifecycle; \method{SingleBrokerMain} uses loopback and an OS-allocated port.}{\pathcode{exercises/src/main/java/io/simplekafka/broker/BrokerHandler.java}: \method{handle(Request)}.}
\lessoncontract{First implement METADATA/PRODUCE/FETCH. An unknown partition has error \method{UNKNOWN_TOPIC_OR_PARTITION}; single-broker mode accepts only epoch 0, and offset-range errors retain their corresponding error codes. A successful produce returns AppendResult; a successful fetch does not pass LEO=HW. An error Reply contains only an error code and a short message, never a stack trace on the wire. The course RpcClient opens a new TCP connection for each request; one business error must not stop the broker from accepting later requests.}
\lessonhints{Dispatch by API type, and complete each request's identity and range checks before accessing the log.}{Check whether an error occurs in the transport, handler, or log layer; responsibilities at different layers must not be swallowed by one another.}{Use a real loopback connection to produce and fetch first, then send a failing request and continue with a valid request.}
\expected{Produce three records over TCP and receive their first/next interval; fetch the same partition and receive three offsets/keys/values with logStart=0 and LEO=HW=3. An unknown partition returns the correct error code, after which a valid fetch over a new TCP request still succeeds. These cases correspond to \method{Step12Test}; you can also observe them manually with \coursecmd{SingleBrokerMain} and \coursecmd{ClientMain} on the command line.}
\pitfalls{Calling only the handler's unit method cannot expose frame-boundary or correlation-id errors; converting an exception into an empty successful response hides errors and breaks client semantics. A real Kafka broker also has authentication, quotas, request-version compatibility, and a persistent control plane; this course's broker binds to loopback, and its API is incompatible with official clients.}
\lessoncommand{12}
\lessonquestions{Why should a broker error reply not expose a Java stack trace?}{Why does single-broker HW=LEO not mean the same rule can be used in replica mode?}
