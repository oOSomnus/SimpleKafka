\chapter{Producing, Consuming, Offsets, and Redelivery}
This chapter turns the teaching program that calls the broker directly into understandable client behavior. The producer buffers messages by partition, the consumer pulls under explicit assignment, and OffsetStore writes processed progress to a local log. The key distinction is among three positions: the broker's LEO, HW in replication mode, and a group's committed offset. A poll advances the client's in-memory position; that is not a commit. A commit also does not mean that broker log data has been deleted. The client takes ownership of the RpcClient passed directly to it and closes it on close; the MetadataRouter passed in is a borrowed shared dependency, and its creator should close it only after all clients using it have been closed.

\lessonsection{13}{Batched Producer}
\goals{Build per-partition ordered batch buffering, threshold-based sending, and explicit flush.}{Understand metadata routing, batch boundaries, returned receipts, and uncertainty about request outcomes.}
\background{A batch for each partition must preserve call order, but different partitions can accumulate independently. send obtains the partition from metadata and synchronously sends that partition's batch when it reaches batchRecords; flush sends all non-empty batches in stable order and aggregates ProduceReceipt values. The receipt returned by an automatic send must not be discarded: retain it and return it to the caller at the next flush. The default ACK is LEADER, and there is no background timer. A timeout or error during the produce RPC/reply path leaves the result unknown: the broker may already have appended the records. Any failure after that path begins enters an “outcome unknown” state; subsequent operations fail until close, rather than guessing and replaying.}
\providededit{RpcClient manages sockets, timeouts, correlation ids, and requests/responses; metadata, Partitioner, and the batch record structure are provided.}{\pathcode{exercises/src/main/java/io/simplekafka/client/SimpleProducer.java}: \method{send(String,byte[],byte[],long)}, \method{flush()}.}
\lessoncontract{Preserve send order within the same partition; batches for different partitions may be independent. Send a partition's batch synchronously when it is full. A receipt stores the topic-partition and [firstOffset,nextOffset); explicit flush returns receipts for both automatic sends and sends performed by that flush. Once the produce RPC/reply path begins, any failure leaves the append outcome unknown: preserve the first error and never replay the batch. Later send, flush, or \pathcode{setAcks} calls report \method{REQUEST_TIMEOUT} until the producer is closed. Failures during metadata lookup or request preparation before that path do not poison the producer.}
\lessonhints{First distinguish “send the request,” “receive confirmation,” and “return the receipt to the caller” as three different points in time.}{Use TopicPartition as the buffer key, and check flush order and behavior for empty batches.}{Make the broker append and then return an error, or delay its response until timeout; verify that the client does not create a second copy.}
\expected{Configure 3 partitions and batchRecords=2. Consecutive records with the same key should route to the same partition and preserve order; null keys should be distributed by per-instance round robin. Reaching two records sends once, and flush returns results that include the automatic-send receipt. After an append-then-error reply, preserve that first error; later send, flush, and \pathcode{setAcks} report \method{REQUEST_TIMEOUT} without replay. See \method{Step13Test} and \method{Step27Test}.}
\pitfalls{If the receipt from an automatic flush is discarded, the caller cannot know which offset range already succeeded; if an RPC/reply failure is treated as proof of no append and retried, duplicates may result. A real Kafka producer has asynchronous I/O, retries, idempotence protocols, and more comprehensive thread-safety guarantees. This course deliberately sends synchronously and does not retry automatically; an unknown outcome is a design choice, not a defect.}
\lessoncommand{13}
\lessonquestions{Why is a timeout insufficient to prove that the broker did not append the records?}{If an error response for the same batch is retried, how could the caller identify a duplicate? Why does this course not implement that mechanism?}

\lessonsection{14}{Pull-Based Consumer}
\goals{Build a single-threaded, single-round pull consumer that explicitly manages assigned partitions and local positions.}{Understand seek, empty fetches, and the shared total budget.}
\background{A consumer's position is the offset of the next record to process or fetch. Manual assign deduplicates and sorts partitions, then replaces the old assignment with a new map: a retained partition keeps its previous position, a revoked partition is removed, and a new partition starts at position=0; it does not read OffsetStore. seek can replay or jump, but does not commit. poll is one bounded request, not a continuous long poll; all partitions share the maxRecords/maxBytes total budget. After records are returned successfully, only the corresponding partitions' positions advance to the last returned offset+1; a failed fetch for a partition must not advance that partition's position. An empty result means that no data is currently readable at that position; it does not mean the consumer should skip ahead. The consumer is used single-threadedly to avoid races on position from concurrent polls.}
\providededit{RpcClient already provides FETCH; \method{SimpleConsumer} holds the group name and partition positions, and provides read-only \method{position(tp)}. Step 14 does not call OffsetStore.}{\pathcode{exercises/src/main/java/io/simplekafka/client/SimpleConsumer.java}: \method{assign(Collection)}, \method{seek(TopicPartition,long)}, \method{poll(int,int)}.}
\lessoncontract{assign deduplicates and stably sorts; positions of retained partitions do not change, new partitions start at 0, revoked entries are removed, and committed offsets are not read. seek requires its target partition to be assigned, or reports \method{NOT_ASSIGNED}. After a successful poll, only partitions represented in returned records advance; an empty fetch changes nothing, and a failed partition does not advance. Reads do not commit automatically. Total records/bytes must not exceed request limits; the broker caps oversized positive \pathcode{maxBytes} to a conservative single-frame budget, and subsequent fetches continue from the first unreturned offset. The returned mapping is organized in predictable partition order.}
\lessonhints{Model “assigned,” “has a position,” and “has a committed offset” separately; do not mix the store into the early manual mode.}{Maintain one remaining poll budget while reading the partitions instead of resetting it for each partition.}{Make a request fail for one of two partitions, then check how the positions of the other, successful partition and the failed partition change.}
\expected{After assigning two partitions, both initial positions are 0; poll reads offsets 0 and 1, then position=2; seek to 0 and poll again to reread 0. An empty fetch leaves position unchanged, and seek on an unassigned partition reports \method{NOT_ASSIGNED}. See \method{Step14Test}.}
\pitfalls{Records returned by poll have not necessarily been durably committed; seek also changes only the local position. Using the full maxBytes for every partition can exceed the total budget. A real Kafka consumer also provides long polling, thread restrictions, and a complex assignment/position lifecycle; this course uses one round at a time and explicitly assumes single-threaded use.}
\lessoncommand{14}
\lessonquestions{Why does advancing position after a successful read still not mean that a restart will begin at the new position?}{If a request for one partition fails, why must the positions of all partitions not be advanced together?}

\lessonsection{15}{Consumer Offset Persistence}
\goals{Persist the offset of the next record to process and restore it in a new consumer.}{Distinguish physical log offsets, the group/tp key, and the message protocol.}
\background{OffsetStore is an append log: each commit encodes (group,TopicPartition,nextOffset) in a LogRecord, and the physical log assigns an increasing offset of its own; the nextOffset stored in the record payload is the consumer progress. key=null and timestamp=0; the provided MessageCodec encodes the OffsetKey/value, and a restart scan finds the latest value for the same key. The underlying store uses the record format and force behavior from Chapter 1, and a damaged tail follows the same recovery rules. consumer.resume first assigns partitions, then looks up the committed value for each one; if no value has been committed, it starts from 0. A consumer offset is the next offset, so after committing 3, recovery resumes by fetching from 3. The broker handler routes \method{COMMIT_OFFSET}/\method{FETCH_OFFSET} requests as well.}
\providededit{Offset-entry encoding in MessageCodec, RpcClient, consumer assignment, and log-record utilities are provided.}{\pathcode{exercises/src/main/java/io/simplekafka/group/OffsetStore.java}: \method{commit(OffsetKey,long)}, \method{fetch(OffsetKey)}; \pathcode{exercises/src/main/java/io/simplekafka/client/SimpleConsumer.java}: \method{resume(Collection)}, \method{commitSync()}; also extend BrokerHandler with \method{COMMIT_OFFSET/FETCH_OFFSET}.}
\lessoncontract{An offset is the index of the next record and can be explicitly moved backward; each group and TopicPartition is independent. Reopening the store after a commit still yields the latest value; a missing value is an empty OptionalLong. If nothing has been committed, resume sets position=0; after a successful fetch, commitSync can commit the positions of all assigned partitions. A group token is used for commit fencing only in Step 20; manual consumption passes null.}
\lessonhints{First define consumer progress as a value, rather than as a physical log-record index.}{When scanning the same OffsetKey, determine which of multiple commits is the final value; do not assume map order.}{Test both a restarted store and a rebuilt consumer, verifying disk persistence and position initialization separately.}
\expected{Read offsets 0, 1, and 2, then commit nextOffset=3; close and reopen OffsetStore, and fetch returns 3; a new consumer resumes from 3, while another group still starts from 0. The physical record offset in the OffsetStore log does not have to equal the 3 in the payload. See \method{Step15Test}.}
\pitfalls{Committing the last processed offset (2) directly causes offset 2 to be read again after restart; confusing a group offset with HW leads to the mistaken belief that a commit makes data visible or invisible. Real Kafka stores offsets in the replicated/compacted internal topic \pathcode{__consumer_offsets}, whereas this course uses a local, single-coordinator append log and provides no HA.}
\lessoncommand{15}
\lessonquestions{Why is a consumer offset conventionally the next offset rather than the last processed offset?}{What does HW control, and what does a group's committed offset control?}

\lessonsection{16}{At-Least-Once Processing}
\goals{Establish a safe ordering between processing side effects and offset commits, and explain redelivery.}{Understand failure and restart, batch positions, and the boundary of commit atomicity.}
\background{In this course, after one poll, ProcessingLoop sorts by TopicPartition and invokes the processor in offset order within each partition. It calls commitSync once for all partitions only if every record returned in that round was processed successfully; if the processor throws an exception, the original exception propagates and no partition is committed. The consumer's in-memory position has already advanced with poll, so the failed instance must not be reused or it could skip records that were not committed; close it and rebuild it from the persisted positions. Side effects and offset commits are not one atomic transaction: if a side effect has happened but the commit has not succeeded, the record will be processed again after restart. At-least-once therefore allows duplicates, but should not silently lose records that were not successfully processed.}
\providededit{The \method{RecordProcessor} callback interface, one-round poll, commitSync, and the consumer lifecycle needed for rebuilding are provided.}{\pathcode{exercises/src/main/java/io/simplekafka/client/ProcessingLoop.java}: \method{runOnce(int,int)}.}
\lessoncontract{Return the number of successfully processed records. Invoke record processing in stable partition order and offset order; commit only after all records have succeeded. Propagate any processor exception unchanged and commit no partitions in that round. After a failure, the caller should close this consumer and rebuild it from the store; do not treat the position already advanced by poll as persisted progress.}
\lessonhints{Write the timeline “poll, external side effect, commit, crash,” then find the one window in which a duplicate can occur.}{For a batch spanning multiple partitions, decide whether committing some partitions would violate this lesson's contract that all processing must succeed before commit.}{Restart once after processing the first record fails and once after all processing succeeds; compare the delivery sequences observed.}
\expected{Processing offset 0 succeeds and processing offset 1 throws an exception; after rebuilding the consumer, it receives 0 and 1 again. After both records are processed successfully and committed, rebuilding again does not redeliver them. Record the first side effect in the test and assert replay of 0/1 and the final offset; see \method{Step16Test}.}
\pitfalls{Swallowing an exception from the processor and then committing causes data loss; continuing to use the failed instance skips replay. At-least-once does not mean exactly-once, and the broker does not automatically provide idempotent external side effects. Real Kafka can atomically process output transactions and offset delivery in specific Kafka workflows; this course has no transactions and does not present its local OffsetStore as a transaction boundary.}
\lessoncommand{16}
\lessonquestions{Why is a duplicate reasonable if a crash occurs after the side effect succeeds but before the offset is persisted?}{To avoid continuing to run a failed consumer, is the key state its in-memory position or its persisted offset? Why?}
