\chapter{Consistency Across Producers, Brokers, and Consumers}

This chapter follows a message across three independent boundaries: producer confirmation, broker replication, and consumer processing. An \textbf{unknown outcome} means the server may have completed an action but its reply did not arrive; retrying the same intention can duplicate it. \textbf{Idempotence} means repeating a request with the same stable identity and content does not add another durable effect; it is not a transaction. At-least-once processing replays uncertain work and therefore permits duplicate effects. A \textbf{side effect} changes state outside the log, such as updating a local ledger. A \textbf{transaction} would commit changes across participants as one indivisible unit; this course has no shared transaction spanning producer, replicated log, consumer offset, and ledger. If exactly-once means one business effect across all those boundaries, they must be coordinated; an ACK, HW, commit, or producer idempotence alone does not provide that guarantee. Experiments use real TCP and independent broker logs, recording physical LEO, authority-reported progress, HW, consumer position, durable committed offset, visible records, and callbacks separately.

\lessonsection{30}{Idempotent Producer}
\goals{Persist producer batch identity so an explicit retry of the same batch returns its original offset range without another append.}{Start with basic identity concepts and connect stamped records, log recovery, replication acknowledgment, routing, and explicit client retry.}
\background{Prerequisites: \stepref{29}{Cross-Layer Experiments}, plus \stepref{1}{Record Format}, \stepref{6}{Segmented Log}, and \stepref{24}{Replicated Writes}. A network error can leave a producer unsure whether the broker appended; without a durable identity, sending again creates a new record. Idempotent append assigns a stable identity to a logical batch so the broker can map an exact retry to its first offsets. Do not confuse four numbers: leader epoch is the broker role term; producer epoch is a caller-managed producer session term; firstSequence is that producer's next batch sequence for this partition; Kafka offset is the record's location in the partition log. eventId identifies a business event and is used in Step31 to deduplicate across offsets.}

\paragraph{Errors, state, and side effects.}Negative producer id/epoch/sequence, null topic-partition/acks, null/empty batch, null record, stamped input, sequence addition overflow, a record over its limit, negative timeout, or an oversized frame is \method{INVALID_REQUEST}; reject before append without consuming sequence. A new producer or higher producer epoch starts at sequence0; a higher epoch becomes durable only with a persisted stamped record. Current epoch accepts only exact nextSequence; an older epoch is \method{FENCED_PRODUCER_EPOCH}, a gap or unrecorded old sequence is \method{OUT_OF_ORDER_SEQUENCE}. For the same completed producerId/producerEpoch/firstSequence, a changed batchSize is \method{OUT_OF_ORDER_SEQUENCE}; with the same batchSize, a different batchHash is \method{DUPLICATE_SEQUENCE_CONFLICT}. An exact full duplicate with the same identity, boundary, and hash returns its original half-open \pathcode{[firstOffset,nextOffset)} range with no append or physical-LEO change. The replicated backend still checks current leader epoch/minISR and performs the full ALL HW wait. If only a matching tail-batch prefix is durable, validate it and append only the missing suffix, returning the original full range; another producer/batch receives \method{INCOMPLETE_BATCH}, while the same identity with changed payload receives \method{DUPLICATE_SEQUENCE_CONFLICT}. A retained start above0 returns \method{PRODUCER_STATE_EXPIRED}.
\paragraph{Teaching frame bound.}API11 uses the course TCP frame from Step11: the length field is in [10,8,388,608] bytes and excludes its 4-byte prefix; payload is at most8,388,598 bytes, total frame at most8,388,612 bytes. Reject a batch request over that bound before sending; the stamped-record bound is independently1,048,580 bytes total.
\paragraph{Derived state and call boundaries.}Producer-state cache is derived from stamped log records. Scan new suffixes incrementally; when prefixVersion changes or LEO moves backward, discard the cache and rebuild from offset0. Recovery reads one complete record at a time with \pathcode{read(offset,1,1_048_580)}, verifying each producer sequence, batch index, and batch hash. Only a final batch may be incomplete; recovery can retain it for matching continuation, while complete invalid history is rejected without rewriting the log. If an uncertain I/O error occurs after storage mutation, do not treat memory state as durable; reopen the failed log and recover. Leader \pathcode{epoch} differs from producer \pathcode{epoch}: after leadership changes, the same producer identity can retry with its original producer epoch.
\paragraph{Client boundaries.}The \pathcode{IdempotentProducer(router,producerId,producerEpoch)} constructor requires nonnegative identity; negative id/epoch is \method{INVALID_REQUEST}. On an open producer, \pathcode{send} also rejects null tp/records/acks, empty batches, null records, negative timeout, stamped input, record/frame overflow, or sequence overflow. Metadata failure before the data RPC is not an unknown append. Once the request could reach the broker, failure leaves a per-partition pending batch; another send to that partition is \method{INVALID_REQUEST}, while other partitions are independent. Only a successful receipt whose range length equals the batch count advances nextSequence and clears pending state. \pathcode{retry(tp)} without pending state is \method{INVALID_REQUEST}; otherwise it explicitly refreshes metadata and sends once to the new route with the same identity, firstSequence, frozen records, ACK mode, and timeout. Refresh/RPC failure or invalid receipt preserves pending state. close clears local pending state but not its borrowed router; send/retry on a closed client throws \pathcode{IllegalStateException}.
\lessoncontract{Only a repeated batch with the same producer identity, batch boundary, and content returns the original durable range; never fabricate a receipt for a failed path. Replication errors do not roll back a stamped record already appended.}

\lessonsection{31}{Idempotent Consumer Effects}
\goals{Apply each stable business event to a durable ledger once even when its Kafka record is delivered repeatedly.}{Explain why offset deduplication and eventId deduplication differ, then implement a recoverable local ledger.}
\background{Prerequisites: \stepref{30}{Idempotent Producer}, plus \stepref{16}{Process Then Commit} and \stepref{29}{Replayed Side Effects}. A Kafka offset identifies one log record's position, not a business event: the same event can be sent to another offset, and a callback can repeat after commit failure. A stable eventId comes from business data; if the same event keeps the same ID through replay and restart, the ledger can use it as an application-level deduplication key. This task coordinates one local forced log and its in-memory balances; it does not share a transaction with Kafka's offset store.}
\providededit{The provided layer supplies \pathcode{BusinessEvent(String eventId,String account,long delta)} (\pathcode{provided/src/main/java/io/simplekafka/model/BusinessEvent.java}) and \pathcode{MessageCodec.encodeBusinessEvent(BusinessEvent):byte[]} / \pathcode{decodeBusinessEvent(byte[]):BusinessEvent} (\pathcode{provided/src/main/java/io/simplekafka/protocol/MessageCodec.java}).}{\pathcode{exercises/src/main/java/io/simplekafka/client/DurableEffectStore.java}: the existing skeleton's \method{public DurableEffectStore(Path directory)} opens a \pathcode{PartitionLog} and invokes recovery first; implement \method{public synchronized boolean apply(BusinessEvent event)} and \method{public synchronized void recover()}. Existing API methods are \method{public synchronized long balance(String account)} and \method{public synchronized void close()}.}
\paragraph{Business event and durable format.}\pathcode{BusinessEvent} requires eventId and account to be non-empty strict UTF-8 strings of at most255 bytes each; delta is any signed long, including positive, negative, or zero. Its value format is \pathcode{version:uint8=1 | eventId:length-prefixed identifier | account:length-prefixed identifier | delta:int64}; unknown version, truncated input, invalid UTF-8/identifier, or trailing bytes returns \method{INVALID_REQUEST} at the codec boundary. The provided \pathcode{BusinessEvent} constructor rejects an invalid identifier with \pathcode{IllegalArgumentException}. The store writes one \pathcode{RecordData(null,encodedEvent,0)} per event: null key, timestamp0, no producer stamp. Ordinary record overhead is32 fixed bytes.
\lessoncontract{\pathcode{apply} on a new valid eventId first computes the account balance with checked addition, then force-appends one record, then publishes the in-memory seen/balance state; it returns true. Replaying the exact same eventId/account/delta returns false and changes neither log nor balance. Reusing the ID with another account/delta is \method{INVALID_REQUEST}; balance overflow is also \method{INVALID_REQUEST}; neither appends.}
\begin{itemize}
\item On a usable store with a complete log, \pathcode{apply(null)} returns \method{INVALID_REQUEST}; an invalid eventId/account cannot form a valid \pathcode{BusinessEvent} (the provided constructor throws \pathcode{IllegalArgumentException}). \pathcode{balance(account)} returns0 for an unseen account; null, empty, invalid-Unicode, or over-255-byte account input returns \method{INVALID_REQUEST}.
\item Calls to apply/balance/recover/close on one store instance are synchronized. Construction and explicit \pathcode{recover()} rebuild identity and balances from offset0 in order, reading one complete record per page (\pathcode{maxRecords=1,maxBytes=1_048_580}); require logStart=0, null key, timestamp0, and no stamp. Complete invalid payload, invalid record fields, conflicting historical ID, balance overflow during replay, or scan without progress returns \method{CORRUPT_RECORD}; complete corrupt history is not rewritten.
\item If the physical tail contains only an incomplete record, PartitionLog/SegmentLog recovery truncates it to the last complete record before replay. A complete record with bad CRC/structure/business encoding is not treated as a partial tail. If identical events already repeat in history, recovery counts their balance once and leaves the existing log records intact.
\item If append I/O or its returned range is uncertain, do not publish a new in-memory balance and mark the instance failed. A truncated ledger (logStart>0) returns \method{CORRUPT_RECORD} and fails the store. After failure or close, apply/balance/recover return \method{STORAGE_ERROR}; close and construct a new instance to recover from disk. close is idempotent.
\end{itemize}

\pitfalls{A forced ledger append coordinates only one local store's log and in-memory publication; it does not form a distributed transaction with the producer, Kafka log, or consumer offset. \lessonquestions{Why is stable eventId a better business deduplication key than Kafka offset or callback count?}{After the ledger append succeeds but consumer offset commit fails, which states are still uncoordinated?}
\paragraph{Self-check answers.}Offset identifies a log position and callback count records attempts; neither identifies one business event across positions. The ledger effect is durable while the commit is not, so callbacks repeat, but eventId makes the ledger return false and prevents another balance change. The consumption position and ledger still were not committed atomically.
