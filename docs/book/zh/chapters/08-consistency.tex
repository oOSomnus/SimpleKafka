\chapter{生产者、broker 与消费者的一致性}

本章沿着同一消息观察三个彼此独立的边界：producer 确认与重试、broker 复制与可见性、consumer 进度与持久化业务副作用。某一边界成功不构成端到端事务。实验使用真实 TCP 连接和每个 broker 独立的日志；观察结果分别记录物理日志末端（LEO）、高水位（HW）、consumer position、已提交 offset 与 processor 回调。

\pathcode{UNKNOWN} 与 \pathcode{POISONED} 两个观察阶段的错误均为 \method{REQUEST_TIMEOUT}；poisoned reuse 在本地被拒绝，不增加 proxy 转发数。

\expected{逐阶段对照真实 cluster 及调用方持有的 recorder/proxy。响应丢失时断言 dropped(PRODUCE)=1、forwarded(PRODUCE)=2：poisoned attempt 不会转发，只有新 producer 的显式重发贡献第二次转发。选举轨迹中的 \pathcode{ELECTED_WITHOUT_TAIL} 仍为 LEO 1/0/0、HW=0，随后 \pathcode{OLD_TAIL_REMOVED} 为 LEO 0/0/0。ALL 故障为 \method{REQUEST_TIMEOUT}；稍后可见不会追溯性地产生 receipt。consumer replay 时断言 rejected(\pathcode{COMMIT_OFFSET})=1、forwarded(\pathcode{COMMIT_OFFSET})=0、effects=[0,0]，新 consumer commit 后真实 \pathcode{FETCH_OFFSET} 返回 1。stale group replay 时旧 token 的两次请求都被 fencing，但 effects 仍为 [0,0]。}
\pitfalls{receipt 证明的是 ACK 结果，不保证 LEADER 已确认但未复制的尾部会在之后的干净选举中保留。timeout 不能证明没有追加。poll 推进 consumer position 早于 group commit；group fencing 保护 broker 操作，不会撤销副作用。这些实验不会给 \method{SimpleProducer} 增加重试，不用 sleep 制造 timeout，也不声称端到端 exactly-once。}

\lessonsection{30}{幂等生产者}
\goals{让每条记录携带可持久化的 producer batch 身份，并使显式重试返回原 offset 区间而不重复追加。}{理解 batch sequence、producer epoch、内容指纹、部分复制，以及为什么重试必须是调用方显式选择。}
\background{原有三参数 \method{RecordData} 构造器仍是普通、非幂等记录的正式入口。新增的 nullable \method{producerStamp} component 是 broker 为幂等请求设置的 metadata。\method{ProducerStamp} 含 \method{producerId}、由调用方管理的 \method{producerEpoch}、\method{firstSequence}、\method{batchSize}、\method{batchIndex} 与 32-byte \method{batchHash}。SHA-256 指纹以流式方式计算 count 以及每条记录的 timestamp、key 长度/key、value 长度/value；不包含 offset 或 leader epoch，并区分 null key 与空 key。该指纹用于验证相同身份的重试是否携带同一 batch。}
合法 stamp 要求 producerId、producerEpoch、firstSequence 非负；batchSize 为正；batchIndex 在 [0,batchSize)；\method{firstSequence+batchSize} 不溢出；hash 恰好 32 bytes。指纹输入为大端 \pathcode{count:int32}，之后逐条输入 \pathcode{timestamp:int64 | keyLength:int32(-1 means null) | key | valueLength:int32 | value}；不包含 offset 或 leader epoch。

已提供的 \method{ProducerStamp.ENCODED_OVERHEAD} 为 64 bytes；磁盘与 \method{MessageCodec} wire 的 1 MiB record 上限均计入这部分开销。
每条 stamped record 都在普通日志记录中保留身份，因此 FETCH、\pathcode{REPLICA_FETCH}、reconciliation 与磁盘恢复会看到相同 metadata。stamped 磁盘布局为 \pathcode{length | crc32c | offset | timestamp | marker:int32=-2 | producerId:int64 | producerEpoch:int32 | firstSequence:int64 | batchSize:int32 | batchIndex:int32 | batchHash:32 bytes | keyLength:int32 | valueLength:int32 | key | value}。它额外占 64 bytes，最小记录总长为 96 bytes；1 MiB 记录上限包含 stamp，CRC32C 覆盖 offset 到 value 末尾。普通未 stamped 字节不变。教学 wire 上的 stamped RecordData 为 \pathcode{marker=-2 | producerId | producerEpoch | firstSequence | batchSize | batchIndex | batchHash[32] | keyLength | key | valueLength | value | timestamp}；普通 wire record 不变。

broker 从保留日志前缀派生去重状态，而不是将它作为新的 authority 真相。它在写入前验证 sequence 与完整 batch hash，记住已完成 batch 的 offset 范围，并允许复制 fetch 追加匹配的部分 batch 后缀。完整重复返回原范围；补齐部分尾 batch 的重试只追加缺失后缀。更高 producer epoch 必须从 sequence 0 开始，且只有实际持久化记录后才生效。同一 batch 身份但 hash 不同会冲突；sequence 跳号、未记录的旧 sequence 或非法边界属于顺序错误。未完成尾 batch 会阻止无关追加，直到原 batch 补齐或正常修复改写前缀。若保留日志起点大于 0，则 producer state 过期，不能猜测恢复。

\lessoncontract{\method{IdempotentProducer.send} 在发出一次 RPC 前固定每分区 sequence 与完整输入 batch 的稳定副本。只有合法成功 receipt 才推进 sequence 并清除 pending。任何请求/回复失败都保留该 batch；同分区的另一 send 必须拒绝，而 \method{retry} 显式刷新 metadata，并使用相同身份、sequence、payload、ACK 模式和 timeout 发出且只发出一次请求。没有后台或自动重试；close 只丢弃本地 pending，不关闭借用的 router。producer id 与 epoch 由调用方提供；重建 client 必须使用更高 epoch 和 sequence 0。\method{IdempotentAppender} 在任何 mutation 前验证所有输入；精确完成批次的重复返回原范围，相同部分批次只追加缺失后缀，同身份但 hash 不同则报 \method{DUPLICATE_SEQUENCE_CONFLICT}。旧 producer epoch 报 \method{FENCED_PRODUCER_EPOCH}；跳号和非法旧 sequence 报 \method{OUT_OF_ORDER_SEQUENCE}；保留前缀缺失报 \method{PRODUCER_STATE_EXPIRED}；未完成尾 batch 时写入无关记录报 \method{INCOMPLETE_BATCH}。持久 mutation 失败或留下不确定状态后，该 log 标记 failed，在重开前不得继续操作。前缀截断或 retention 会使派生 cache 失效；恢复时重新扫描并验证保留历史。wire API id 为 11，即 \method{IDEMPOTENT_PRODUCE}，请求字段为 \method{tp, epoch, acks, timeoutMillis, producerId, producerEpoch, firstSequence, records}；成功响应复用既有 \method{ProduceBody}。空、超大、非法或已 stamped 的 client batch 必须无副作用地拒绝。此 API 只由 replicated backend 支持，单 broker backend 不支持。重复请求仍需通过 ACK precheck 并等待完整 ACK 条件，包括 ALL 的 minISR、epoch、HW 与 deadline 规则。}
日志派生状态按 producer id 记录最高的已持久化 epoch、next sequence、已完成 batch 的 identity/范围；整个 partition 至多有一个未完成尾 batch。未知 producer 或更高 epoch 必须从 sequence 0 开始；当前 epoch 的新 batch 必须恰好从已保存的 next sequence 开始。恢复用有界批次读取并校验 batch 连续性与 hash；prefix version 不变时只重放新后缀。前缀改变或 LEO 回退时丢弃 cache 并从 offset 0 重建；恢复报错会使派生状态失效，不能跳过损坏历史。
client 细节：pending batch 只阻止同一 partition 的另一 \method{send}，其他 partition 相互独立。成功 receipt 必须恰好覆盖该 batch 的记录数，才能推进 sequence。\method{retry} 在没有 pending batch 时报告 \method{INVALID_REQUEST}；metadata 刷新失败和非法回复均保留 pending state，retry 使用刷新后的当前 leader epoch。重复 batch 仍执行 ACK precheck 与完整 ACK wait。
\lessonhints{区分三种身份：leader epoch 围栏 broker 角色，producer epoch 围栏 producer 会话，sequence 标识该 producer 会话内的 batch。}{把日志视作持久真相，把内存 producer-state cache 视作带版本的重放结果。}{测试一个完整重复、同 sequence 不同内容冲突、一个部分 batch 续传，以及 leader 切换后的显式重试；同时检查 receipt 区间与 stamped 磁盘记录。}
\expected{发送多条 batch 后以相同身份和 payload 重试：两个 receipt 指向相同 half-open 区间，重复时物理 LEO 和 stamped bytes 均不变；下一 sequence 则从后续 offset 追加。首个回复丢失后，将记录复制至 HW、选举干净的新 leader，再显式重试，取得原范围且每个 broker 仍只有一份。将某 broker 的日志从磁盘重开后，以相同 raw 请求再发送，仍返回原范围。重复 ALL 请求在范围高于 HW 时仍会 timeout，只有复制并确认该范围后才能成功。}
\pitfalls{这是调用方提供的教学身份；它没有实现 Kafka PID 分配、transaction coordinator 或 client session WAL。新的 producer id 不会去重重复业务事件，业务 event id 也不是 producer sequence。\method{SimpleProducer} 仍是非幂等且从不重试；只有调用方调用 \method{retry}，新 \method{IdempotentProducer} 才重试。幂等追加不会强化 ISR、HW 或选举假设，也不会形成端到端 exactly-once 保证。}

已提供的 store API 为 \pathcode{DurableEffectStore(Path)}、\pathcode{synchronized boolean apply(BusinessEvent)}、\pathcode{synchronized long balance(String)}、\pathcode{synchronized void recover()} 与 \pathcode{synchronized void close()}；close 可重复调用。
已提供的构造器会打开本地日志，并在 store 可用前通过 \method{recover()} 重建状态。
\lessoncontract{将 \pathcode{<directory>} 用作本地 \method{PartitionLog}。每个事件只生成一条 \method{RecordData(null,encodedEvent,0)}，先 force 追加记录，再发布内存状态。首次遇到合法 event id 时，先用 checked addition 计算账户新余额，再追加一次，随后把完整事件写入 \method{seen} 并更新余额；返回 true。event id、account、delta 完全相同的重放返回 false，不改日志或余额。同 event id 不同内容或余额溢出时报告 \method{INVALID_REQUEST}，且不追加。\method{recover} 按保留 offset 顺序重建两个 map，并要求 logStart=0、key=null、timestamp=0、没有 producer stamp。它解码每个 payload、验证 event identity，相同重复事件恢复时只计一次；完整非法记录、冲突 id、余额溢出或扫描无进度报告 \method{CORRUPT_RECORD}。apply、balance、recover、close 在同一 store 实例 monitor 下同步。追加失败且持久化结果未知时，不发布新内存余额并将 store 标记为 failed；后续操作报告 \method{STORAGE_ERROR}，调用方必须 close 并从磁盘重建。}
恢复以有界读取按 offset 顺序扫描保留账本；物理尾部不完整时遵循底层日志的恢复规则，完整但格式非法的记录则拒绝。
store 已关闭或失败后，\method{apply}、\method{balance} 与 \method{recover} 均报告 \method{STORAGE_ERROR}；\method{close} 可幂等重复调用。
\lessonhints{event id 必须来自业务事件，并在不同 Kafka offset 与进程重启后保持不变。}{写日志前先校验 event id 冲突和 checked balance；只有追加成功后才发布内存状态。}{consumer 关闭并重开后，从新的消费位置重放同一事件，再同时比较余额与账本记录。}
\expected{处理事件 A（account +10）、第二条携带相同 A 的 Kafka record，以及事件 B（account -3）。第一个 A 与 B 各追加一次；重复 A 返回 false，余额为 7，账本事件为 [A,B]。若首轮 commit 失败，重建 consumer 并重放 offset 0、1、2；验证 callback history 为 [0,1,2,0,1,2]、账本仍是两条事件、余额为 7，committed offset 为 3。stale generation 可以拒绝 commit，却不能撤销已持久化副作用。}
\pitfalls{该 store 只让单个本地账本追加与内存发布保持一致；它与 Kafka 或 consumer offset store 没有共享事务。同一事件可以触发多次 callback，包括出现在不同 offset 的记录。group fencing 会拒绝旧 token，但不能回滚副作用。这是单个本地 store 的应用层幂等记账，不是分布式事务、全局账本或端到端 exactly-once 保证。}
